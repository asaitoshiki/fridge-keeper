# 冷蔵庫管理アプリ 開発依頼書（v1.0）

Androidアプリを新規開発してください。以下の仕様に従って実装をお願いします。
**実装前に必ず「進め方」セクションを読み、フェーズごとに区切って進めてください。一度に全部書かないこと。**

---

## 1. プロダクト概要

### コンセプト
**「食品ロスを減らすアプリ」**

単なる在庫管理アプリではない。「冷蔵庫の中身を管理する」ではなく「**食材を腐らせない・捨てない**」ことをアプリのアイデンティティに置く。既存の在庫管理アプリが飽和しているため、ポジショニングをロス削減側に振ることで差別化する。

### ターゲット
一人暮らし〜少人数世帯。ユーザー本人の端末で完結する（アカウント登録・共有機能なし）。

### コアバリュー
賞味期限・消費期限を管理し、**腐らせる前に気づかせる**こと。

### 設計上の最重要課題
冷蔵庫アプリが使われなくなる最大の原因は「**入力が面倒 → 在庫と現実がズレる → 使わなくなる**」という離脱。
したがって全機能は「**入力の手間を増やさない**」ことを最優先の判断基準とする。機能追加の際も常にこの原則で判断すること。

## 2. 技術スタック

| 領域 | 採用技術 |
|---|---|
| 言語 | Kotlin |
| UI | Jetpack Compose |
| ローカルDB | Room |
| 設定保存 | DataStore (Preferences) |
| 定期処理・通知 | WorkManager + NotificationManager |
| カメラ | CameraX |
| バーコード読み取り | ML Kit Barcode Scanning（オンデバイス） |
| ウィジェット | Jetpack Glance |
| DI | Hilt |
| 非同期 | Coroutines / Flow |

### 重要な制約
- **完全ローカル完結**。サーバー通信は一切行わない。外部APIも使用しない。
- **AI/LLMは使用しない**。
- ユーザーデータは端末外に一切送信しない。

---

## 3. アーキテクチャ

Google推奨の **MVVM + Repository** の薄い構成を採用する。過剰な抽象化はしない（YAGNI）。

```
ui/          Compose画面 + ViewModel
domain/      ビジネスロジック（期限計算、ストリーク判定など）
data/        Room Entity/DAO、Repository、DataStore
```

- ViewModelはUiStateをStateFlowで公開し、Composeはそれを購読するだけにする
- Repositoryがデータソースを隠蔽する
- 単方向データフローを守る

## 4. データモデル

### FoodItem（食材）

```kotlin
id: Long
name: String
category: FoodCategory
storageLocation: StorageLocation
expiryType: ExpiryType
expiryDate: LocalDate?   // ★null許容（後述）
quantity: Int
registeredAt: LocalDate
janCode: String?
memo: String?
```

#### ★ expiryDate を null 許容にする理由（重要・必読）

本プロジェクトの方針として「攻撃的プログラミング（存在すべき値は直接アクセスし、防御的なnull許容をしない）」を採用しているが、
**`expiryDate` の null 許容は例外ではなく、正当なドメインモデリングである。**

理由：野菜・肉・魚など**期限が印字されていない食品が現実に存在する**ため。「期限が未設定」という状態はエラーではなく正常な業務状態。

したがって：
- `expiryDate` を必須（non-null）にしてはならない
- 「登録時に期限入力を必須にする」UIにしてはならない
- 他のフィールドについては通常どおり攻撃的プログラミングの方針に従うこと

### 実効期限（推定期限）のロジック

```
実効期限 = expiryDate ?: (registeredAt + プリセット日数)
推定フラグ = (expiryDate == null)
```

- プリセット日数は **category × storageLocation** の組み合わせで決まる（後述のテーブル）
- 推定期限はDBに保存せず、**参照時にdomain層で導出する**
- 推定期限で表示する箇所には、UI上に必ず「**目安**」バッジを表示すること（安全上の理由。第8章参照）

### Enum定義

```kotlin
enum class FoodCategory { VEGETABLE, FRUIT, MEAT_FISH, DAIRY, EGG, PROCESSED, FROZEN, SEASONING, DRINK, OTHER }
enum class StorageLocation { FRIDGE, FREEZER, VEGETABLE_DRAWER, ROOM_TEMP }
enum class ExpiryType { BEST_BEFORE, USE_BY, UNKNOWN }  // 賞味期限 / 消費期限 / 不明
```

`ExpiryType` を分けるのは安全上重要。**消費期限（USE_BY）は過ぎたら食べてはいけない**ため、賞味期限より強い警告表示にする。

### JanProductDictionary（バーコード辞書）

```kotlin
janCode: String  // PK
productName: String
defaultCategory: FoodCategory?
lastUsedAt: LocalDate
```

外部APIを使わず、**ユーザーが一度入力した商品名を端末内に蓄積**して次回以降の自動補完に使う。使うほど賢くなる仕組み。

### ConsumptionLog（消費・廃棄履歴）

```kotlin
id: Long
name: String
category: FoodCategory
type: ConsumptionType  // EATEN / DISCARDED
quantity: Int
date: LocalDate
```

ストリーク（食品ロスなし継続日数）と統計の算出に使う。

### FrequentItemTemplate（よく買うものテンプレート）

```kotlin
id: Long
name: String
category: FoodCategory
storageLocation: StorageLocation
expiryType: ExpiryType
defaultQuantity: Int
sortOrder: Int
```

## 5. プリセット期限テーブル

`category × storageLocation → 日数` のマップを定数として定義する。初期値は以下（v1.0ではハードコードでよい。ユーザー編集機能はv1.1）。

| カテゴリ | 冷蔵 | 冷凍 | 野菜室 | 常温 |
|---|---|---|---|---|
| 野菜 | 7 | 30 | 7 | 5 |
| 果物 | 7 | 30 | 7 | 5 |
| 肉・魚 | 2 | 30 | – | – |
| 乳製品 | 7 | 14 | – | – |
| 卵 | 14 | – | – | 7 |
| 加工食品 | 7 | 30 | – | 30 |
| 冷凍食品 | – | 90 | – | – |
| 調味料 | 90 | – | – | 90 |
| 飲料 | 7 | – | – | 30 |
| その他 | 7 | 30 | 7 | 7 |

該当する組み合わせが未定義の場合は、期限なし扱い（アラート対象外）とする。

## 6. v1.0 機能仕様

### 6.1 ホーム画面（期限順リスト）
- **期限が近い順**に食材を一覧表示する。これがアプリの心臓部
- 緊急度で色分けする：

| 状態 | 表示 |
|---|---|
| 期限切れ | 赤（強調）。消費期限の場合はさらに強い警告表示 |
| 当日〜1日前 | 赤 |
| 2〜3日前 | オレンジ |
| 4〜7日前 | 黄 |
| それ以降 | 通常色 |
| 推定期限 | 「目安」バッジを付け、彩度を落とす |

- 保管場所でのフィルタを付ける
- 各アイテムから**ワンタップで「食べた」「捨てた」**を実行できること（6.4）

### 6.2 食材の登録
以下3経路。すべて**期限は任意入力**（未入力ならプリセット推定）。

**(a) 手動入力** — 商品名・カテゴリ・保管場所・期限種別・期限日・個数・メモ

**(b) バーコードスキャン** — CameraX + ML KitでJANコードを読む
- 辞書にヒット → 商品名・カテゴリを自動補完（期限は別途入力/推定）
- **ヒットしない場合が必ずある**ので、その際は商品名を手入力させ、確定時にJAN辞書へ保存する
- スキャン失敗・カメラ権限拒否時のフォールバック（手動入力へ誘導）を必ず用意する

**(c) テンプレートから登録** — よく買うものをワンタップで登録。入力削減の要

### 6.3 まとめ通知
- **1日1回、設定時刻に1通だけ**通知する（個別通知の連発はしない）
- 内容：閾値日数以内に期限を迎える食材の件数と代表名（例：「今日ヤバい食材が3つあります：にんじん 他」）
- 対象が0件の日は通知しない
- WorkManagerのPeriodicWorkRequestで実装
- Android 13+ の `POST_NOTIFICATIONS` 権限リクエストに対応すること

### 6.4 ワンタップ消費／廃棄
- 「**食べた**」…在庫を減らす（数量1減、0で削除）。ConsumptionLogにEATENを記録
- 「**捨てた**」…在庫から削除。ConsumptionLogにDISCARDEDを記録し、**ストリークをリセット**
- 誤タップ対策として、実行後に Undo できるスナックバーを出すこと

### 6.5 食品ロスなし継続日数（ストリーク）
- `今日 - 最後にDISCARDEDを記録した日` を継続日数として算出（記録がなければ利用開始日から）
- ホーム画面上部に目立つ形で表示する
- 「捨てた」を記録すると0にリセットされる
- 過去最高記録も保持・表示する

このアプリの世界観の中心。ポジティブな動機付けとして機能させる。

### 6.6 通知タイミングのカスタマイズ
- 通知時刻（デフォルト 8:00）
- 何日前から通知するか（デフォルト 3日前）
- 通知のON/OFF
- DataStoreに保存

### 6.7 ホーム画面ウィジェット
- Jetpack Glanceで実装
- 期限が近い順に上位3〜5件を表示。緊急度の色を反映
- タップでアプリを開く
- 継続率に最も効く機能。アプリを開かなくても情報が届く状態を作る

### 6.8 データのエクスポート／インポート
- 全データをJSONで書き出し／読み込み
- Storage Access Framework (SAF) を使い、ユーザーが保存先を選ぶ
- 端末故障・機種変更でデータが失われるリスクへの対策（ローカル完結の裏返し）
- インポート時は「上書き」か「マージ」かをユーザーに選ばせる

## 7. スコープ外（v1.0では実装しないこと）

以下は**意図的に除外**している。勝手に実装しないこと。

- ❌ AI / LLM連携（コスト・外部依存を避けるため）
- ❌ レシートOCR読み取り（AIなしでは実用精度に届かない。かつレシートに期限情報は無い）
- ❌ 外部API連携（商品DB照会など）
- ❌ アカウント・ログイン・クラウド同期・家族共有
- ❌ レシピ提案
- ❌ 栄養成分・アレルギー情報の表示（**安全上、意図的に扱わない**）
- ❌ 広告・課金（v1.1で実装。ただしUI設計時に将来の広告枠を阻害しないこと）
- ❌ 冷蔵庫イラストUI（v1.1の目玉として予定。ただしデータモデルは対応可能なままにしておく）

## 8. 安全設計・免責（最重要）

**食品を扱うアプリであり、健康被害に直結しうる。以下は必ず実装すること。**

### 8.1 免責事項の表示
- **初回起動時に同意画面**を表示し、同意しないと利用開始できないようにする（同意状態はDataStoreに保存）
- **設定画面内にも常時「免責事項」を配置**する

文面（叩き台。開発者が最終確認・調整する前提）：

> 本アプリが表示する期限および目安日数は一般的な参考情報であり、食品の実際の安全性を保証するものではありません。実際の日持ちは、購入時の鮮度・開封の有無・保管温度等により大きく変動します。
> 喫食の可否は、必ずご自身で食品の状態（見た目・におい等）を確認してご判断ください。
> また、端末の状態により通知が遅延・不達となる場合があり、通知の到達およびデータの保全を保証するものではありません。
> 本アプリの利用により生じたいかなる損害についても、開発者は一切の責任を負いません。

### 8.2 UI側での安全担保
免責文だけに頼らず、UIでも「保証ではない」ことを伝える。

- 推定期限には**必ず「目安」バッジ**を表示する
- **消費期限（USE_BY）は賞味期限より強い警告表示**にする（消費期限は過ぎたら食べてはいけないため）
- 「まだ食べられます」等、安全を断定する文言は**絶対に表示しない**
- 期限内であることを緑色などで「安全」と印象づける表現は避ける

### 8.3 通知は不達前提で設計する
Doze・メーカー独自の省電力機能により、Androidの通知は確実には届かない。
**アプリを開けば必ず全体の状態が把握できる**設計にし、通知はあくまで補助と位置づけること。

## 9. コーディング方針

プロジェクトのCLAUDE.mdに従うこと。特に以下を厳守：

- **コメントは日本語**で、コードブロックの概要やコードで表現できない背景を簡潔に書く
- **既存コードを読んでから書く**（編集対象だけでなく呼び出し元・依存先・類似実装も確認）
- **現状優先** — 既存の構造・パターンを理解し、必要最低限の変更で実装する
- **YAGNI** — 現時点で不要な機能は実装しない。「将来使うかも」で作らない
- **最小依存** — クラス間の依存を最小限に保つ
- **攻撃的プログラミング** — 存在すべき値は直接アクセスする。防御的な存在チェック・null許容は書かない。フレームワークが保証する値の検証は不要
  - **ただし `expiryDate` の null は正当なドメイン状態**であり、この例外に該当しない（第4章参照）
- **条件分岐を避ける** — フラグ制御は最終手段。早期リターン／ガード節で浅く保つ

## 10. 進め方

**一度に全部実装しないこと。** 以下のフェーズに区切り、各フェーズの完了ごとに動作確認できる状態にしてください。

**Phase 1: 基盤**
プロジェクト構成、Room + Entity/DAO、Repository、Hilt設定、Enum・プリセット期限テーブルの定義

**Phase 2: コア機能**
食材の手動登録／編集／削除、期限順ホーム画面、緊急度の色分け、推定期限の導出ロジック

**Phase 3: 消費とストリーク**
ワンタップ消費／廃棄、ConsumptionLog、食品ロスなし継続日数の表示

**Phase 4: 通知**
WorkManagerによるまとめ通知、通知設定画面、権限リクエスト

**Phase 5: 入力削減**
バーコードスキャン（CameraX + ML Kit）、JAN辞書、テンプレート機能

**Phase 6: 仕上げ**
ウィジェット（Glance）、エクスポート／インポート、免責同意画面、設定画面
